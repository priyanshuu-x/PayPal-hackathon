# ProofCheck API contract

Owner: Session A (backend). Session B builds the frontend against this file and mocks any endpoint not yet merged. Change it in the same PR as any endpoint change. Items marked **TBC** are confirmed in the Phase 0 spikes (`docs/architecture.md`).

Base path: `/api`. JSON unless stated. Money is a **decimal string** (`"49.99"`) with a separate `currency`. Timestamps are ISO 8601 UTC (`2026-11-03T10:15:00Z`).

## Conventions

**Errors** (all non-2xx):
```json
{ "error": { "code": "validation_error", "message": "Human-readable, generic", "case_id": "optional" } }
```
Codes: `validation_error` 422, `unauthenticated` 401, `forbidden` 403, `csrf_failed` 403, `not_found` 404, `conflict` 409 (stale `version` or wrong state), `rate_limited` 429, `payload_too_large` 413, `upload_rejected` 400, `upstream_error` 502, `internal_error` 500. PayPal and Groq error bodies are never returned.

**Merchant auth:** `POST /api/auth/login` sets an HttpOnly, Secure, SameSite=Lax session cookie. Every merchant endpoint needs it. Every `POST` made as the merchant also needs header `X-CSRF-Token` (value from `GET /api/auth/me`). Frontend requests use `credentials: "include"`.

**Buyer (store) endpoints** need no login. The server issues an anonymous buyer-session cookie on the first store call; `GET /api/store/orders` returns only that session's orders.

**Rate limits** (per client IP, per minute unless noted; the reply is `429 rate_limited` with a `Retry-After` header in seconds, so show "try again in N seconds"): login 10; refund uploads 5 per 10 minutes; creating or capturing a store order 30; `GET /api/store/sdk-config` 30; evidence uploads 20 per 10 minutes; webhooks 300; every other `/api` call 240; `/api/health` is exempt. The Copilot has its own limit (20 questions per 10 minutes per merchant) and login also locks after 5 wrong passwords for the same email and IP. Handle `429` on every call: a busy browser tab can reach 240 requests a minute if it polls too fast (poll a case no faster than every 2 seconds).

**Request size:** at most 10.25 MB for an upload (`POST /api/refunds`, `POST /api/cases/{id}/evidence`) and 1 MB for anything else; larger requests get `413 payload_too_large` before the body is read.

**Response headers:** every reply carries `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, cross-origin isolation headers and `Cache-Control: no-store` (and HSTS over HTTPS). The API serves JSON and images only, never HTML, so none of these affect normal use. There are no `/docs`, `/redoc` or public OpenAPI pages.

**Data retention:** uploaded files, extracted text and forensic notes, the buyer's reason and email, the payer's name in the record snapshot and the Copilot's question history are deleted 30 days after creation (`RETENTION_DAYS`). Cases, checks, verdicts and the audit log stay. After that, `GET /api/cases/{id}/evidence` returns `404` and a dispute case with a removed document cannot be approved until the document is added again.

**Text from models** (`reasons`, `draft.text`, Copilot `answer`) is plain text. Render it as plain text only.

## Shared types

```ts
type Verdict = "MATCHES_RECORDS" | "NEEDS_REVIEW" | "DOES_NOT_MATCH_RECORDS";
type CaseStatus = "new" | "processing" | "ready" | "approved" | "declined" | "error";
type CaseSource = "refund" | "dispute";
type Severity = "critical" | "major" | "minor" | "info";

interface CheckResult {
  field: string;                 // "order", "amount", "date", "items", "merchant", "payer", "shipping", "delivery", "embedded_instructions", "reused_file"
  claimed: string | null;
  actual: string | null;
  result: "match" | "mismatch" | "unknown";
  severity: Severity;
  note: string;                  // plain-language reason
}

// A short refund note (at most 240 characters) that is sent to the buyer with the refund.
// Generated by the model from PayPal record fields only, then checked: every number, date and
// ID must exist in PayPal's record and accusing words are not allowed. After three failed tries
// a fixed template is used. The merchant may edit it; edits go through the same check.
interface Draft {
  text: string;
  grounded: boolean;
  unsupported_values: string[];
  edited_by_human: boolean;
}

interface CaseSummary {
  id: string;
  source: CaseSource;
  status: CaseStatus;
  verdict: Verdict | null;
  risk_score: number | null;     // 0-100
  amount: string | null;
  currency: string | null;
  paypal_order_id: string | null;
  created_at: string;
  version: number;
}

interface CaseDetail extends CaseSummary {
  capture_id: string | null;
  refund_id: string | null;     // set once a refund case is approved; always null for disputes
  evidence_count: number;       // documents attached (dispute cases)
  dispute: {                    // null for refund cases
    reason: string | null;      // PayPal reason code, for example MERCHANDISE_OR_SERVICE_NOT_RECEIVED
    status: string | null;      // PayPal dispute status
    response_due: string | null;
  } | null;
  dispute_id: string | null;
  checks: CheckResult[];
  forensic_notes: string[];
  paypal_record: {               // verified PayPal fields shown on the "PayPal says" side
    order_id: string; amount: string; currency: string; created: string;
    items: { name: string; quantity: number; unit_price: string }[];
    payer_name: string | null; shipping_status: string | null; tracking_number: string | null;
  } | null;
  draft: Draft | null;
  audit: { at: string; actor: string; action: string; hash: string }[];
  audit_chain_valid: boolean;
}
```

## Auth (merchant)

| Method and path | Body | Response |
|---|---|---|
| `POST /api/auth/login` | `{email, password}` | `200 {merchant_id, csrf_token}` and session cookie (8 hours). Wrong email or password: `401` with the same generic message. 5 failures in 5 minutes for the same IP and email: `429`. `503` if the server has no `SESSION_SECRET` or merchant credentials configured |
| `POST /api/auth/logout` | - (needs `X-CSRF-Token`) | `204`, session cookie cleared |
| `GET /api/auth/me` | - | `200 {merchant_id, csrf_token}` or `401` |

The merchant email and password hash come from `.env` (`DEMO_MERCHANT_EMAIL`, `DEMO_MERCHANT_PASSWORD_HASH`). Create the hash with `python -m app.security.auth` and paste the output.

SDK v6 setup (confirmed against the sandbox, Phase 0 spike 4): the server fetches a short-lived browser-safe **client token**; the browser calls `paypal.createInstance({ clientToken })`. Order create and capture always go through our backend, never straight to PayPal from the browser.

| Method and path | Body | Response |
|---|---|---|
| `GET /api/store/products` | - | `200 [{id, name, price, currency, image}]` |
| `GET /api/store/sdk-config` | - | `200 {client_id, client_token}` (sandbox, public values only; the token is cached server-side for about 10 minutes) |
| `POST /api/store/orders` | `{items:[{product_id, quantity}], shipping:{name, address_line_1, address_line_2?, admin_area_2, admin_area_1, postal_code, country_code}}` | `200 {order_id, amount, currency}`. **Prices are computed server-side** from the catalog plus a flat shipping fee of `4.99`. Any extra field (for example `price`) is rejected with `422`. 1 to 10 lines, quantity 1 to 10 per product (lines for the same product are merged) |
| `POST /api/store/orders/{order_id}/capture` | - | `200 {order_id, capture_id, status: "COMPLETED", amount, currency}`. Call it after the buyer approves in the PayPal flow. `404` if the order belongs to another buyer session; `409` if the buyer has not approved yet or the total differs; `502` on a PayPal failure. Repeating the call returns the same result without capturing twice |
| `GET /api/store/orders` | - | `200 [{order_id, capture_id, status: "created"\|"captured", amount, currency, created_at, items: [{name, quantity, unit_price}]}]` (this buyer session only, newest first) |

## Refund requests (buyer upload)

`POST /api/refunds` (multipart/form-data): `order_id` (string), `reason` (string, max 1000), `email` (optional), `file` (PNG, JPEG, WebP or PDF, max 10 MB).
-> `202 {case_id}`. The case starts as `status: "new"` and analysis starts in the background (Render Workflows when configured, otherwise a local task). Status goes `new`, `processing`, then `ready` with a verdict, usually within a few seconds but up to about 30 s. Poll `GET /api/cases/{id}` as the merchant. If analysis crashes the status is `error` and the merchant can use `reanalyze`. Anything the system cannot verify (PayPal unreachable, unreadable document, daily AI limit reached) ends as `ready` with verdict `NEEDS_REVIEW` and a major check explaining why.

- Must be sent from the buyer session that paid for the order (same cookie as the store): `404 not_found` for an order that is not yours or does not exist; `409 conflict` if the order is not paid yet or a refund request for it is already open (`new`, `processing`, `ready` or `approved`).
- Files are validated by magic bytes (the filename and client MIME type are ignored), size (10 MB), image pixel count and PDF page count (20). Rejected files return `400 upload_rejected` with a short reason. Encrypted PDFs and PDFs with scripts or embedded files are rejected.
- Field errors (reason over 1000 characters, malformed email, order ID over 64 characters) return `422 validation_error`.

## Cases (merchant)

| Method and path | Notes |
|---|---|
| `GET /api/cases?status=&verdict=&source=&limit=&cursor=` | `200 {items: CaseSummary[], next_cursor}` |
| `GET /api/cases/{id}` | `200 CaseDetail` |
| `GET /api/cases/{id}/evidence` | Returns a re-encoded PNG preview with all metadata removed, at most 2000 px per side (`Cache-Control: private, no-store`; needs the merchant session; never a public path). Use it as an `<img src>`. PDFs return `404` until page rendering lands in A5 |
| `POST /api/cases/{id}/reanalyze` | Needs CSRF. Runs the analysis again (after an error, or a temporary PayPal or AI outage). `200 CaseSummary` with `status: "new"`; poll `GET /api/cases/{id}` until `ready`. `409` for approved or declined cases, and for a case analysed within the last 10 minutes that is still `processing`. Never moves money |
| `POST /api/cases/{id}/approve` | Body `{action: "approve" \| "decline", version: number, draft_text?: string}`; any other field is rejected (there is no way to choose an amount). Needs a merchant session and CSRF. `200 CaseDetail` with `status: "approved"` and `refund_id` (a full refund of the capture, sent with idempotency key `<case_id>:approve`), or `status: "declined"` (nothing is sent to PayPal). `409` for a stale `version`, a case that is not `ready` (including a double click), a refund case with no payment, a dispute case with no dispute ID, or an attached document that is missing. `422` when the edited note fails the grounding check or is longer than the limit (240 characters for a refund note, 1500 for a dispute note); the message names the problem. `502` when PayPal cannot complete the action: the case goes back to `ready` with a new `version`, so reload it and try again; retrying is safe and never acts twice. **On a dispute case, approve sends the evidence response to PayPal** (the order's tracking number and carrier when PayPal has them, the note, and any attached documents) and `refund_id` stays `null`; it never accepts the buyer's claim. This is the **only** endpoint that moves money or sends evidence |
| `POST /api/cases/{id}/evidence` | Dispute cases only. multipart/form-data with one `file` (PNG, JPEG, WebP or PDF, 10 MB, same checks as refund uploads). Needs CSRF. `201 {evidence_count}`. At most 3 documents per case (`409` beyond that, for a refund case, or for an approved or declined case). Documents are stored privately and sent to PayPal only when the merchant approves |

## Case Copilot (merchant, read-only)

| Method and path | Notes |
|---|---|
| `POST /api/cases/{id}/copilot` | Body `{question}` (1 to 500 chars; other fields are rejected). Needs CSRF. `200 {answer, tools_called: string[]}`; `answer` is **plain text** (render it as text only; control characters and Markdown emphasis are already stripped, at most 2000 characters) and `tools_called` lists the PayPal lookups it made (`get_order_details`, `list_disputes`, `get_dispute`, `get_shipment_tracking`, `list_transactions`). Max 5 lookups per question; 20 questions per 10 minutes per merchant (`429`). `503` when the server has no AI key. The Copilot can only read: it cannot approve, refund, accept a dispute, change a verdict or send anything, and asking it to just gets a refusal. It sees the case summary and verified check results, never the uploaded document's text, the buyer's message or the draft. Answers can take 1 to 15 seconds |
| `GET /api/cases/{id}/copilot` | `200 [{question, answer, tools_called: string[], created_at}]`, oldest first, at most 50 |

## Webhooks (PayPal -> backend)

`POST /api/webhooks/paypal` - PayPal-signed (the five `PAYPAL-*` signature headers are required). Verified with the verify-webhook-signature API before anything is stored; unverified, malformed or oversized (over 1 MB) -> `400`; duplicate event ID -> `200 {"status":"duplicate"}` and ignored. Other responses: `200 {"status":"accepted"}` (a handled type) or `200 {"status":"ignored"}`. Needs `PAYPAL_WEBHOOK_ID`; without it every webhook is rejected. Handled: `CUSTOMER.DISPUTE.CREATED`, `CUSTOMER.DISPUTE.UPDATED`, `CUSTOMER.DISPUTE.RESOLVED`. Only the dispute ID in the event is used: the server fetches the dispute and its order from PayPal itself, creates a `source: "dispute"` case (status `new`, then analysed like a refund case) or updates the existing one. Buyer-written dispute messages are never read. If the dispute cannot be fetched the event is not recorded and the response is `502`, so PayPal retries it. Not called by the frontend.

### Dispute analysis (what the checks mean)

There is no uploaded document for a dispute; PayPal's own dispute data stands in for the claim. The checks that matter are against PayPal's order record: the order exists, the disputed capture belongs to it, and for the reason `MERCHANDISE_OR_SERVICE_NOT_RECEIVED` the order's tracking status. **Tracking that shows `delivered` against a "not received" claim is a major mismatch, so the verdict is `NEEDS_REVIEW`**: it flags a dispute the merchant may want to contest, and the draft is an evidence note citing the tracking number. A dispute that cannot be linked to an order is `NEEDS_REVIEW`, never a denial. The draft note (at most 1500 characters) goes through the same grounding check as refund notes.

### Demo mode (off by default)

Real sandbox disputes can only be opened by a buyer in PayPal's UI. When the server runs with `DEMO_MODE=true`, `POST /api/demo/disputes` (merchant session and CSRF) takes `{order_id}` of a paid demo-store order and creates a demo dispute case (`dispute_id` starts with `DEMO-`, reason not received). It goes through the same analysis and approve handler, but approving sends nothing to PayPal. `201 {case_id, dispute_id}`; `404` for an unpaid or unknown order; `409` if a dispute case for the order is already open. Without `DEMO_MODE` this endpoint does not exist (`404`). Real webhooks are still signature-verified.
